Eight technologies I build with every day. Keep scrolling: each station lights up in 3D as the request passes through it.

STATION 01UI · COMPONENTS

React

Interfaces as components.

I build interfaces in React as small, composable components. State lives where it is used, hooks share behaviour without inheritance, and Suspense keeps loading states clean, so even data-heavy dashboards stay easy to change.

  • Components
  • Hooks
  • Context
  • Suspense
  • React Query
LiveStats.jsx
function LiveStats({ campaignId }) {
  const { data, isLoading } = useQuery({
    queryKey: ['stats', campaignId],
    queryFn: () => getStats(campaignId),
  });
  if (isLoading) return <Skeleton />;
  return <StatGrid items={data} />;
}
STATION 02FRONTEND · RENDERING

Next.js

The front door.

Next.js is where people meet the system. I use the App Router with Server Components and streaming to keep pages fast, static and incremental rendering to keep them cheap, and route handlers so the browser talks to the API through a thin, typed edge.

  • App Router
  • Server Components
  • SSR · SSG · ISR
  • Route handlers
app/campaigns/[id]/page.tsx
export default async function Page({ params }) {
  const { id } = await params;
  const data = await fetch(`${API}/campaigns/${id}`, {
    next: { revalidate: 60 },
  }).then((r) => r.json());
  return <CampaignView data={data} />;
}
STATION 033D · WEBGL

Three.js

Depth on the web.

Three.js is how I bring 3D into the browser, including this page. Scenes, cameras and lights built in code, physical materials and environment maps for realistic surfaces, and a render loop tied to scroll and pointer so motion feels connected to the person using it.

  • Scenes & cameras
  • PBR materials
  • 3D type
  • Scroll-driven motion
scene.js
const scene = new THREE.Scene();
const camera = new THREE.PerspectiveCamera(42, w / h, 0.1, 140);
const mesh = new THREE.Mesh(geometry, material);
scene.add(mesh);

renderer.setAnimationLoop((t) => {
  mesh.rotation.y = t * 0.001;
  renderer.render(scene, camera);
});
STATION 04API · ARCHITECTURE

NestJS

Structure for the backend.

When an API needs to grow, I reach for NestJS. Modules keep each domain separate, dependency injection keeps services testable, and guards, pipes and interceptors handle auth, validation and caching once, in one place, instead of in every route.

  • Modules & DI
  • Guards
  • Validation pipes
  • Interceptors
  • WebSocket gateways
campaigns.controller.ts
@Controller('campaigns')
@UseGuards(JwtAuthGuard)
export class CampaignsController {
  constructor(private readonly svc: CampaignsService) {}

  @Get(':id')
  findOne(@Param('id') id: string) {
    return this.svc.findOne(id);
  }
}
STATION 05RUNTIME · I/O

Node.js

The runtime underneath.

Node.js runs the APIs, workers and real-time services. Its event loop handles thousands of concurrent connections without blocking. I use streams for heavy payloads and separate worker processes for jobs that shouldn't slow down a request.

  • Event loop
  • Streams
  • Worker processes
  • WebSockets
import-events.js
import { pipeline } from 'node:stream/promises';

await pipeline(
  createReadStream('events.ndjson'),
  parseLines(),
  batch(500),
  writeToMongo(),
);
STATION 06MEMORY · SPEED

Redis

Speed at the edge of memory.

Redis sits between the API and the databases. I use it for cache-aside reads with TTLs, rate limiting with atomic counters, background job queues, and pub/sub to push live updates out to every connected client.

  • Cache-aside
  • TTL invalidation
  • Rate limiting
  • Queues
  • Pub/Sub
campaigns.service.ts
const key = `campaign:${id}`;
const hit = await redis.get(key);
if (hit) return JSON.parse(hit);

const doc = await Campaign.findById(id).lean();
await redis.set(key, JSON.stringify(doc), 'EX', 60);
return doc;
STATION 07DOCUMENTS · ANALYTICS

MongoDB

Data shaped like the product.

I model data in MongoDB around how it is read: embedded documents where data travels together, references where it doesn't, compound indexes for the hot queries, and aggregation pipelines that turn raw events into analytics.

  • Schema design
  • Compound indexes
  • Aggregations
  • Transactions
analytics.pipeline.js
db.messages.aggregate([
  { $match: { tenantId, sentAt: { $gte: since } } },
  { $group: { _id: '$status', total: { $sum: 1 } } },
  { $sort: { total: -1 } },
]);
STATION 08RELATIONAL · INTEGRITY

MySQL

Relational where it counts.

When data has strict relationships, like users, billing, orders and permissions, I reach for MySQL. Normalised schemas with foreign keys, indexes checked with EXPLAIN, and transactions so a multi-step write either fully happens or doesn't happen at all.

  • Foreign keys
  • Indexes & EXPLAIN
  • Joins
  • ACID transactions
debit-wallet.sql
START TRANSACTION;
UPDATE wallets SET balance = balance - 50
  WHERE user_id = 42 AND balance >= 50;
INSERT INTO ledger (user_id, amount, type)
  VALUES (42, -50, 'debit');
COMMIT;

How the pieces work together in a typical product I build: render, route, cache, persist, and push updates live.

READ PATH

Cache first.

A React page rendered by Next.js asks the NestJS API for data. Redis answers straight from memory when it can; on a miss the API reads the database and warms the cache with a TTL.

Next.js→NestJS→Redis→DB
WRITE PATH

The right store.

NestJS pipes validate the payload. Flexible documents go to MongoDB, strictly related records go to MySQL inside a transaction, and the matching Redis keys are cleared.

NestJS→MongoDB · MySQL→Redis DEL
REAL-TIME PATH

Push, don't poll.

Node.js workers publish events through Redis pub/sub, and a WebSocket gateway sends them to every open Next.js client.

Node.js→Redis Pub/Sub→WebSocket
